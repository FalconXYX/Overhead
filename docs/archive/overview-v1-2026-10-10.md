# Overhead — Development Brief

Oct 10, 2026 · @Parth

Working title. A live sky-camera overlay with a linked ground map, built with React, TypeScript, OpenLayers and Zustand. Written to be handed to a coding agent.

## Summary & goals

Overhead draws satellites, the ISS, the Moon, planets and bright stars on top of live sky-camera video, beside a linked OpenLayers ground map. It is a portfolio piece for a map-focused role, so every feature is chosen to show OpenLayers, React, TypeScript, Zustand and OGC standards working on real public data.

The core idea: a camera at a known place, pointing in a known direction, is a map projection of the sky. Anything whose direction we can compute (satellites from orbital elements, planets from ephemerides, stars from a catalog) can be drawn into the frame.

Two views share one clock:

- **Sky view:** the camera image or video with computed objects drawn over it.
- **Ground map:** the camera site, satellite ground tracks, the camera's view projected up to orbit height, satellite cloud imagery and terrain.

### Success criteria

1. After calibration, bright stars and planets land within 0.5° of where the camera shows them.
2. After stream-delay calibration, the ISS and other bright satellites land within 1°.
3. Selecting an object in either view highlights it in the other on the next frame.
4. The UI holds 60 fps on a laptop with the ISS, the CelesTrak visual group and Starlink loaded.
5. No API keys and no backend: static hosting plus one scheduled data-fetch job.
6. A 5-minute demo covers video, imagery, terrain, sensor controls and OGC standards.

### Out of scope

- A 3D globe. This is a 2D OpenLayers project on purpose.
- Accounts, auth or a database.
- Downloading, re-hosting or redistributing anyone else's camera video or images. Third-party feeds are embedded or displayed from their source only.
- Survey-grade astrometry. The goal is a convincing, honest overlay.

### Talking points the code should make easy to show

- **A camera is a map projection.** A rectilinear lens is a gnomonic projection; a fisheye lens is an azimuthal one (equidistant, equal-area, stereographic or orthographic). Unit tests prove the closed-form code matches proj4.
- **Same math as ISR video annotation.** Project known world objects into a camera with a known pose and lens model.
- **Space domain awareness framing.** A ground optical sensor checks what it sees against the satellite catalog.
- **Two-step calibration.** Stars fix pointing because they move only 15° per hour. Satellites fix the stream delay because the ISS crosses about 1° per second overhead.
- **Performance by design.** Orbit propagation runs in a Web Worker, and React renders only on discrete state changes.

## Architecture

One clock in a vanilla Zustand store drives two imperative OpenLayers maps; heavy math runs in Web Workers, and React renders only the panels.

&#91;embedded content: architecture · how data reaches the two maps\]

Arrows show data flow. The store and the workers feed the map bindings, which update both OpenLayers maps; React panels only read the store and send actions.

### Integration rules

1. Create each `ol/Map` once, in an effect on a container ref. Keep it in a module-level registry, never in React state or the store. On unmount call `map.setTarget(undefined)` and dispose its layers.
2. Map bindings in `src/map/sync` subscribe to store slices with `store.subscribe(selector, listener, { equalityFn: shallow, fireImmediately: true })` and mutate OpenLayers objects directly. Every binding returns an unsubscribe function.
3. The clock tick never re-renders React. A component that shows time uses a hook that samples the store at 4 Hz.
4. One `requestAnimationFrame` loop (`src/state/clockLoop.ts`) advances `clock.simTimeMs` from the wall-clock delta times `rate`. In live mode, overlay time = `Date.now() - streamDelayMs`.
5. `propagation.worker.ts` owns all satrecs. At 10 Hz it receives `{ timeMs, observer }` and returns transferable `Float32Array`s (azimuth, altitude, range, sub-satellite lat/lon, sunlit flag). The main thread interpolates between samples for smooth 60 fps motion.
6. `horizon.worker.ts` builds the terrain horizon profile once per camera site.
7. Everything in `src/domain` is pure TypeScript: no DOM, no OpenLayers, no store. It is all unit-tested.

## Time, coordinates & astronomy math

Every object is reduced to one pair before it reaches a map: azimuth in degrees clockwise from north, and altitude in degrees above the horizon, at a UTC time in epoch milliseconds.

### Conventions

- **Time:** `number` UTC epoch ms everywhere. Build a `Date` only at library boundaries. The UI shows UTC and the camera's local time, both labelled.
- **Units in names:** `azDeg`, `altRad`, `rangeKm`, `heightM`. Degrees in the store and UI; radians only inside domain functions.
- **Observer:** `{ latDeg, lonDeg, heightM }`. satellite.js wants `{ latitude, longitude }` in radians and `height` in km. astronomy-engine wants `new Observer(latDeg, lonDeg, heightM)`.
- **Azimuth:** both libraries already use clockwise from north. satellite.js computes `atan2(-topE, topS) + π` (radians, 0 to 2π); astronomy-engine's `Horizon` and `HorizonFromVector` return degrees with east = 90.

### Satellites (satellite.js 7.1.0, in the worker)

1. `const satrec = json2satrec(omm)` once per object.
2. `const pv = propagate(satrec, date)`. It returns `null` on error or decay: skip the object and log `satrec.error`.
3. `const gmst = gstime(date)`, then `const look = ecfToLookAngles(observerGd, eciToEcf(pv.position, gmst))`.
4. Ground map position: `eciToGeodetic(pv.position, gmst)`, then `degreesLat` and `degreesLong`.
5. Sunlit: `const f = shadowFraction(sunPos(jday(date)).rsun, pv.position)`. 0 means fully lit and 1 means umbra; treat `f < 0.5` as sunlit.
6. Visible: sunlit, and the Sun is below −6° at the observer, and the satellite is above the terrain horizon at its azimuth.
7. Scale: a plain loop is fine for a few hundred objects at 10 Hz. Switch a group to `BulkPropagator` (WASM) once a benchmark shows the loop over 4 ms per tick.

### Sun, Moon and planets (astronomy-engine 2.1.19)

- `const eq = Equator(Body.Jupiter, date, observer, true, true)`, then `Horizon(date, observer, eq.ra, eq.dec, 'normal')`. The result's `azimuth` and `altitude` are degrees; `'normal'` corrects for refraction.
- Draw Sun, Moon, Mercury, Venus, Mars, Jupiter, Saturn and Uranus. Size labels by `Illumination(body, date).mag`.
- Twilight for demo planning: `SearchAltitude(Body.Sun, observer, -1, start, 1, -6)` finds evening civil twilight; direction `+1` finds the morning one.

### Stars

- `scripts/build-stars.ts` converts the Yale Bright Star Catalog to `public/data/stars.json` as rows of `[raDegJ2000, decDegJ2000, vmag, hr, name]`, limited to V ≤ 6.5.
- Precompute each star's unit vector once with `VectorFromSphere(new Spherical(dec, ra, 1), t)`.
- Once per second: `const rot = Rotation_EQJ_HOR(t, observer)`. For each star, `HorizonFromVector(RotateVector(rot, v), 'normal')` gives `lon` = azimuth and `lat` = altitude, in degrees. One matrix, thousands of cheap rotations.
- Test fixture, verified while writing this brief: from Maunakea (19.8253°, −155.4689°, 4,204 m) at 2026-10-10T08:00Z, Polaris lands at azimuth 0.59°, altitude 20.15°.

### Direction vectors

Azimuth A and altitude h become a local east-north-up unit vector:

```latex
\hat d_{ENU} = (\cos h \sin A,\; \cos h \cos A,\; \sin h)
```

At observer latitude φ and longitude λ, the ECEF direction is:

```latex
\hat d_{ECEF} = \begin{pmatrix} -\sin\lambda & -\sin\varphi\cos\lambda & \cos\varphi\cos\lambda \\ \cos\lambda & -\sin\varphi\sin\lambda & \cos\varphi\sin\lambda \\ 0 & \cos\varphi & \sin\varphi \end{pmatrix} \hat d_{ENU}
```

### Camera view at orbit height (ground map)

- Sample about 16 points along each image edge. Convert each pixel to azimuth and altitude with the inverse lens model, then to an ECEF ray from the observer's ECEF position O.
- Intersect each ray with a sphere of radius R + H, where H is 420 km for the ISS or 550 km for Starlink (a dropdown):

```latex
t = -(O \cdot \hat d) + \sqrt{(O \cdot \hat d)^2 - (\lVert O \rVert^2 - (R + H)^2)}
```

- Convert the hit points to latitude and longitude (a spherical Earth is accurate enough here) and draw the polygon. A satellite's ground track crossing this patch is about to appear in the video.

### Ground tracks

- Selected satellite: ±10 minutes around the clock in 20-second steps. Others in view: ±3 minutes.
- Unwrap longitudes so consecutive points never jump by more than 180°. Hawaii tracks cross the antimeridian, and OpenLayers draws unwrapped lines correctly across wrapped worlds.

## Camera model & calibration

Treat azimuth as longitude and altitude as latitude on a unit sphere. A rectilinear camera is then a gnomonic projection centred on its pointing direction, and a zenith-pointing fisheye is a polar azimuthal projection.

### Lens models

Here θ is the angle from the optical axis (for a zenith fisheye, θ = 90° − altitude) and f is the focal length in pixels.

| Lens                       | Radius on the sensor | proj4 definition                                                    |
| -------------------------- | -------------------- | ------------------------------------------------------------------- |
| Rectilinear (the StarCams) | r = f tan θ          | `+proj=gnom +lat_0=<alt0> +lon_0=<az0> +x_0=0 +y_0=0 +R=1 +no_defs` |
| Fisheye, equidistant       | r = f θ              | `+proj=aeqd +lat_0=90 +lon_0=0 +x_0=0 +y_0=0 +R=1 +no_defs`         |
| Fisheye, equisolid         | r = 2f sin(θ/2)      | `+proj=laea +lat_0=90 +lon_0=0 +x_0=0 +y_0=0 +R=1 +no_defs`         |
| Fisheye, stereographic     | r = 2f tan(θ/2)      | `+proj=stere +lat_0=90 +lon_0=0 +x_0=0 +y_0=0 +R=1 +no_defs`        |
| Fisheye, orthographic      | r = f sin θ          | `+proj=ortho +lat_0=90 +lon_0=0 +x_0=0 +y_0=0 +R=1 +no_defs`        |

Verified against proj4 2.22.0 while writing this brief:

- With source `+proj=longlat +R=1 +no_defs`, the closed-form gnomonic below matches proj4 to 5 × 10⁻¹⁶, and every fisheye radius matches its formula exactly.
- proj4 2.22.0 returns `NaN` from `gnom` and `laea` unless `+x_0=0 +y_0=0` are present. Always include them.
- No mirroring is needed. This mapping already gives the view from inside the sky: facing west, azimuth 300° lands on the right of the frame, as it does in a real camera.
- For zenith fisheyes proj4 puts north at the bottom and east on the right. A roll of 180° gives the usual north-up, east-left all-sky image.

### Forward model (sky to pixel)

Rectilinear step, for a camera pointing at azimuth A₀ and altitude h₀:

```latex
\cos c = \sin h_0 \sin h + \cos h_0 \cos h \cos(A - A_0)
```

```latex
x = \frac{\cos h \sin(A - A_0)}{\cos c}, \qquad y = \frac{\cos h_0 \sin h - \sin h_0 \cos h \cos(A - A_0)}{\cos c}
```

Cull any point with cos c ≤ 0: it is behind the camera. Fisheyes use the polar projection from the table instead, scaled by f. Both then share the same tail: roll ρ, radial distortion, focal length, principal point, optional flip.

```latex
x' = x\cos\rho - y\sin\rho, \quad y' = x\sin\rho + y\cos\rho, \quad s = 1 + k_1 r^2 + k_2 r^4, \quad r^2 = x'^2 + y'^2
```

```latex
u = c_x \pm f\,s\,x', \qquad v = c_y - f\,s\,y'
```

Here u and v are pixels with v pointing down, and the sign of the u term flips when `flipX` is set. For rectilinear lenses, f = (W/2) / tan(HFOV/2). The sky map uses a pixel projection like the OpenLayers static-image example, so a feature's coordinate is `[u, H - v]`.

The inverse (pixel to sky) undoes the tail, solving distortion with 5 Newton steps, then calls proj4's `inverse`. Only the orbit-height footprint needs it; picking compares projected positions in pixels.

### Calibration flow (the sensor-controls panel)

1. Pause on a frame with stars. Fix pointing first: stars move only 15° per hour, so stream delay does not matter yet.
2. Start from the camera's defaults. Overlay stars to V ≤ 4, the planets and the Moon.
3. **Manual:** sliders plus keyboard nudges for azimuth, altitude, roll, focal length, k1 and principal point.
4. **Assisted:** click a star in the image, then its catalog marker (or pick from the 3 nearest), to make a pair. With 4 or more pairs, fit azimuth, altitude, roll, f, cx, cy and k1 by Levenberg–Marquardt on pixel residuals. Show RMS in pixels and degrees; drop pairs beyond 3σ.
5. **Stream delay:** wait for a bright satellite or the ISS and drag `streamDelayMs` until the marker sits on the moving dot. Re-check whenever the stream restarts.
6. Persist per camera in `localStorage` (inside `try/catch`), with JSON export and import. The pose part exports as GeoPose.

### GeoPose export

- Use OGC GeoPose 1.0 (document 21-056r11), the Basic-YPR form. Position is latitude and longitude in degrees plus height in metres above the WGS-84 ellipsoid. Angles are yaw, pitch and roll in degrees: rotations about the local Up, North and East axes, applied in that order, starting from an East-North-Up frame.
- Take the JSON key names from the official schemas at `https://schemas.opengis.net/geopose`, and validate every export with ajv.
- The standard's text does not spell out yaw's zero direction or sign in the parts checked for this brief. Derive them from the rotation definition, document the choice in `geopose.ts`, and add a round-trip test.
- astronomy-engine's `Observer` height is above mean sea level, while GeoPose height is above the ellipsoid. Label which one each field holds; the difference does not matter for overlay accuracy.

## Terrain

Terrain does two jobs: a horizon profile that hides objects behind real ridges in the sky view, and a ground-map hillshade lit by the Sun's position at the clock time.

### Elevation source

- AWS Terrain Tiles, Terrarium PNGs: `https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`. Free, no account. Credit the sources listed in the dataset's attribution document.
- Decode, with channels 0–255: elevation in metres = R × 256 + G + B / 256 − 32768.
- Browser access (CORS) could not be checked while writing this brief. Check it on first load. If it is blocked, `scripts/fetch-terrain.ts` pre-fetches each site's tiles into `public/data/terrain/`.

### Horizon profile (`horizon.worker.ts`)

1. Fetch tiles around the site: zoom 12 within 5 km, zoom 10 out to the march limit. Decode them with `createImageBitmap` and `OffscreenCanvas.getImageData`.
2. Camera height z₀ = ground elevation at the site + the mast height from `cameras.json`.
3. For each azimuth from 0° to 359°, march outward from 100 m. Use 30 m steps near the camera, growing to 1% of the distance. Sample elevation bilinearly.
4. At distance d with terrain height z, the apparent angle includes Earth curvature and refraction (κ ≈ 0.13):

```latex
\alpha = \arctan\!\left(\frac{z - z_0 - d^2 (1 - \kappa) / (2R)}{d}\right)
```

5. The horizon for that azimuth is the largest α on the ray. Return a `Float32Array(360)` in degrees and store it in `data.horizonProfileDeg`.
6. March limit: 100 km for valley sites. For summit sites, march 250 km so the sea horizon is reached. From Maunakea's 4,204 m, the profile is negative almost everywhere, dipping about 2° below level; that is correct.
7. In the sky view, project the profile through the camera model as a filled skyline. Dim anything below it and flag it "behind terrain" in the inspector.

Test with a synthetic DEM: a 1,000 m wall 10 km away, seen from 0 m, must give 5.67°.

### Hillshade lit by the real Sun (ground map)

- A `WebGLTile` layer over an `XYZ` source of the same tiles, with `crossOrigin: 'anonymous'` (WebGL needs it).
- OpenLayers band values arrive in 0..1, so scale by 255 inside the style expression:

```ts
const elevation = (dx = 0, dy = 0) => [
  "-",
  [
    "*",
    255,
    [
      "+",
      ["*", 256, ["band", 1, dx, dy]],
      ["band", 2, dx, dy],
      ["/", ["band", 3, dx, dy], 256],
    ],
  ],
  32768,
];
```

- Slope and aspect come from neighbour samples via the band offsets, as in the OpenLayers "WebGL Shaded Relief" example.
- Style variables `sunAzDeg` and `sunAltDeg` come from astronomy-engine at the clock time. Push them with `layer.updateStyleVariables(...)` at most once per second.
- When the Sun is below 0°, switch to fixed 315°/45° lighting and show a small "night" badge.

## Feature spec & UI

The sky view takes the larger left pane and the ground map the right, with a timeline across the bottom; below 900 px wide the two views stack.

### Sky view

The background depends on the camera kind:

- **youtube:** the YouTube IFrame Player in a 16:9 box, with a transparent OpenLayers map on top. All map interactions are off and the view is locked to the image extent. Only features take pointer events; everything else passes through to the player. The iframe is cross-origin, so never try to read its pixels.
- **still-image:** an `ImageStatic` layer in the pixel projection with extent `[0, 0, W, H]`, reloaded every `refreshSec` with a cache-busting query. Pan and zoom are allowed. Use the image's own capture time when it is published, not the fetch time.
- **local-video:** a `<video>` element whose frames are drawn into an `ImageCanvas` source, calling `source.changed()` from `requestVideoFrameCallback`. Overlay time = `startUtcMs + currentTime × 1000`. Pan and zoom are allowed.

Layers, top to bottom:

1. Selection halo and labels.
2. Satellites: the ISS emphasised; sunlit and shadowed objects differ in both colour and shape. Trails for the last 30 s and a dotted path for the next 2 minutes.
3. Sun, Moon and planets, labelled.
4. Stars to V ≤ 4.5 by default, sized by magnitude.
5. Altitude/azimuth grid every 10°, with cardinal letters on the horizon.
6. Terrain skyline from the horizon profile.

An "incoming" chip appears when a satellite's ground track will enter the camera's orbit-height footprint within 60 s. Hovering any object shows its name, NORAD ID (satellites), azimuth, altitude, range, lit state and magnitude where known.

### Ground map (EPSG:3857)

- GIBS daily true colour for the clock's UTC date, plus GIBS coastline and label overlays (IDs from capabilities).
- GOES-West infrared at 60% opacity, Time = the clock rounded down to 10 minutes and clamped to the newest available step, labelled "Imagery as of HH:MM UTC".
- Sun-lit hillshade (see Terrain).
- Camera site marker with a wedge showing its horizontal field of view.
- The camera's view at orbit height, with a 420 km / 550 km dropdown.
- Satellite positions (switch to `WebGLVector` above 2,000 points) and ground tracks for the selected and in-view satellites.
- Optional: the day/night terminator, built from the subsolar point.

### Panels

- **Timeline:** live/replay toggle, play/pause, rate (1×, 10×, 60×, 600×), a ±12 h scrubber, a "Now" button, twilight markers and ticks where GOES imagery exists.
- **Camera picker:** every entry in `cameras.json`, with live, offline or daytime status.
- **Calibration (the sensor-controls panel):** sliders with numeric inputs, the star-pair list with residuals, a Fit button, the RMS readout, a stream-delay slider with ±10 s fine control, Reset, Export JSON and Export GeoPose.
- **Layers:** one toggle per entry in `LayersState`.
- **Inspector:** the selected object's details, plus "Show on map" and "Follow".
- **Stretch, tracking mount:** pick a target and watch a simulated mount chase it with a 3°/s slew limit and an acceleration limit. Show its field-of-view box in the sky view and the pointing error over time. An overhead ISS pass shows why the limits matter.

### Interactions

- A click in either view sets `selection.selectedId`, and both views highlight it on the next frame.
- Keys: Space play/pause · ←/→ step 1 s (Shift: 1 min) · `[` `]` change rate · C calibration · L layers · Esc clear selection. In calibration, arrows nudge azimuth and altitude by 0.05° (Shift: 0.5°).
- Shareable URLs carry the state, for example `?cam=subaru-starcam&t=2026-10-10T15:30:00Z&sel=sat:25544`.
- Accessibility: every control is keyboard-reachable with a visible focus ring; `prefers-reduced-motion` turns off trail animation; meaning never rides on colour alone.

## Testing, performance & gotchas

All math is pinned by fixtures, CI never calls a third-party service, and the hot path allocates nothing per frame.

### Unit tests (Vitest)

- **Lenses:** closed form vs proj4 for all five models at 50 random points (difference < 10⁻⁹). Forward then inverse round trip < 10⁻⁶ px. Orientation: facing west, azimuth 300° lands in the right half; a zenith fisheye at roll 180° puts north at the top and east on the left.
- **Astronomy:** Polaris fixture (azimuth 0.59°, altitude 20.15° from Maunakea at 2026-10-10T08:00Z). Planets against a JPL Horizons table within 0.05°. Twilight times within 1 minute.
- **Orbits:** the ISS reference-pass fixture; `propagate` returning `null` is handled; antimeridian unwrapping; ray–sphere intersection (a ray straight up hits at height H).
- **Terrain:** Terrarium decode (R 128, G 0, B 0 gives 0 m); the synthetic wall gives 5.67°; flat sea seen from 4,204 m gives −1.94°, reached about 248 km out.
- **GeoPose:** ajv validation against the official schema, plus a round trip.

### End-to-end tests (Playwright)

- The app loads with no console errors and both maps render.
- The time slider changes the GIBS Time parameter.
- Selecting the ISS in the inspector highlights it in both views.
- Calibration export downloads valid JSON.
- Route mocks serve CelesTrak fixtures, GIBS tiles and a stub YouTube iframe, so CI never hits a real service.

### Performance budgets

| Work                           | Rate                        | Budget                                               |
| ------------------------------ | --------------------------- | ---------------------------------------------------- |
| Map updates on the main thread | 60 fps                      | ≤ 6 ms per frame                                     |
| Satellite propagation (worker) | 10 Hz, interpolated between | ≤ 4 ms per tick before switching to `BulkPropagator` |
| Stars, planets, Sun, Moon      | 1 Hz                        | ≤ 2 ms                                               |
| React commits while playing    | 4 Hz time readout only      | 0 other commits (check with the React Profiler)      |

Reuse `Feature` objects and update geometries in place. Call `source.changed()` once per frame, not per feature. Reuse typed-array buffers between worker ticks.

### Gotchas

- **Stream delay:** live overlays are wrong by seconds until `streamDelayMs` is calibrated. For still images, use the capture time.
- **proj4 2.22.0:** `gnom` and `laea` return `NaN` without `+x_0=0 +y_0=0`. Use the spherical source `+proj=longlat +R=1 +no_defs`.
- **OpenLayers pixel space:** y points up, so a pixel (u, v) becomes `[u, H - v]`.
- **YouTube:** the iframe is cross-origin, so overlay only. Live IDs change on restart, and a channel can disable embedding. Fall back to replay mode.
- **CORS:** a camera JPEG without CORS headers still displays in `ImageStatic` with the Canvas renderer, but it taints the canvas. Never call `getImageData` on it or feed it to WebGL. Terrain tiles need CORS for the WebGL hillshade.
- **CelesTrak:** browsers never call it, and the job stops on the first error.
- **Catalog numbers:** OMM only. Never assume 5-digit NORAD IDs in parsing, regexes or column widths.
- **GOES:** imagery arrives about 40 minutes late and can have gaps. Treat a 404 tile as "no data" and fall back to the previous step.
- **Daytime and cloud:** the overlay still draws positions. Label the view "daytime" or "clouded out"; demos use replay.
- **Refraction:** stars and planets use `'normal'`. Pass satellite altitudes below 10° through astronomy-engine's `Refraction('normal', alt)` so everything near the horizon bends the same way.
- **Mirrored all-sky images:** expose `flipX`.
- **Credits:** show each feed's attribution on screen at all times. Never download or re-host a feed.
- **TypeScript 7:** confirm the lint and test tooling supports it before relying on it.

## Demo script & working agreement

The demo opens on a recorded pass so it never depends on Hawaiian weather; live video is the closing bonus if it is twilight on Maunakea.

### Five-minute demo

1. **0:00 · Replay.** Play a recorded StarCam clip of an ISS or Starlink pass. Labels ride the moving dots. Line: "Every label comes from public orbital data; nothing is placed by hand."
2. **0:45 · Linked views.** Click the ISS in the video. The ground map highlights its track crossing the camera's orbit-height footprint, and the "incoming" chip flags the next satellite.
3. **1:30 · Sensor controls.** Open calibration: the star fit and its RMS, then the stream-delay slider. Line: "The lens is a map projection; stars fix pointing, satellites fix time."
4. **2:30 · Imagery.** Turn on GOES-West infrared at the same moment: the clouds in the camera match the satellite view. Scrub time to show the WMTS Time dimension updating.
5. **3:15 · Terrain.** Switch to the Walenstadt all-sky camera: the computed skyline traces the ridge, a satellite sets behind it, and the hillshade is lit by the real Sun.
6. **4:00 · OGC.** Export the camera pose as GeoPose and show it passing schema validation.
7. **4:30 · Architecture.** Two maps, one clock, workers for the math, no React renders per frame. Then switch to live video if the timing is right.

`?demo=1` runs this tour automatically with captions, in case the network misbehaves on the day. Keep a screen recording of the full tour as a last-resort backup.
